# Phase 6.1 — Balancing Metrics Instrumentation Implementation Plan

**Goal:** Record selected observations for `game-design/balancing.md`'s measurement windows. Gather one to two weeks of normal use before large tuning changes. No balance values change in this phase.

**Architecture:** Local append-only Drift `MetricEvents`, a storage repository, and a safe `MetricsRecorder` entry point for all instrumentation. Gameplay never reads metrics. No aggregation, dashboard, export UI, or cloud upload.

**Baseline:** Phase 5.1 Trail Supplies and Phase 6 backup are implemented. Drift schema is currently 7; this phase upgrades it to 8. Recheck current code before editing. The balancing document defines measurement goals; this plan defines the implemented subset.

## Global constraints

- Gameplay does not await metrics reads or writes. Metrics failures must not change gameplay results, produce a gameplay `Err`, or prevent UI refresh. Shared database resources can affect latency; zero performance impact is not guaranteed. Keep payloads small and check responsiveness.
- All production instrumentation uses `MetricsRecorder.record`. Only the recorder calls `MetricsRepository.logEvent`; no direct repository logging from UI, controllers, or use cases.
- Metrics live in `lib/core/metrics/`. Use existing gameplay results/repositories; introduce no Supabase or Health Connect calls.
- Local-only and disposable is accepted. Metrics are excluded from `CloudGameSnapshot`; uninstall/clear-data loses them and restore cannot recover them. Existing events are not merged with cloud history.
- Observe one tester/account per continuous window. Manually record window boundaries after restore/account changes and label debug-seeded sessions. No automatic account/window tracking or cross-device population analysis.
- Logging is best-effort, not a reward ledger. Process termination can lose pending events. Never replay gameplay to recover metrics.
- No emails, raw Health Connect records, or raw exceptions in payloads. Report instrumentation failures through `AppLogger` without dumping payloads.
- Commit each completed implementation task in its owning repository. This user authorization overrides the standing no-commit rule for implementation of this plan. Stage only task-owned changes. No co-author line or `Co-Authored-By` trailer; never push. Test execution remains subject to the repository's test authorization rule. Unrun checks remain unchecked.

## Measurement coverage

| Question | Evidence | Limit |
| --- | --- | --- |
| Steps seen per local date | Retained HealthDaily.totalSteps | Latest value, not every correction |
| Newly rewardable Steps | health_sync per-day deltas and aggregate | Activity date differs from sync observation date |
| Energy earned | Positive energy_credited events | Startup reconciliation unmeasured; zero-gain conversions remain in health sync |
| Energy spent | Successful adventure_attempt.energySpent | Best-effort history |
| Energy before/after attempts | Observed UI/controller state and returned Player | Before-state may be stale; not an atomic ledger |
| Ending Energy and pending Steps | Current Player | No historical daily-ending snapshots |
| Attempts/rejections by tier and Supplies | adventure_attempt identity/outcome | Includes UI preflight rejection, one event per handled interaction |
| Quest claims/expiries | quest_claimed and per-instance quest_rollover | Original Quest dates retained separately |
| Quest progress/completion rates | Retained dated Quest instances | Current progress/status, no completion timestamps or missed-day assignments |
| EXP/Gold earned and Gold spent | Actual grants/costs in successful events | Never sum quoted rewards as grants; not complete accounting |
| Current Level/Gold | Current Player or existing backup | Not historical distributions or daily level-up counts |
| Claim delay, daily level-ups, exact daily endings | Deferred | Requires additional timestamps/history |
| Inactivity and earning-to-spending delay | Manual observations/event timestamps | Gaps do not prove inactivity; sync time is not walking time |

## Canonical interfaces and storage

`MetricsRepository` provides:

```dart
Future<Result<bool>> logEvent({
  required String eventType,
  required Map<String, Object?> payload,
  required DateTime occurredAt,
});
```

`MetricsRecorder` is constructed with a repository and optional injectable clock. Its public method is:

```dart
void record({
  required String eventType,
  required FutureOr<Map<String, Object?>?> Function() buildPayload,
  DateTime? now,
});
```

Capture observation time synchronously (`now` or the clock), then schedule payload building/storage without making gameplay await it. Catch clock errors, synchronous/asynchronous builder errors, repository throws, failed Futures, and `Err` results. Null payload means skip. No failed Future may escape to gameplay or become an unhandled error on storage shutdown.

The async builder allows a metrics-only Quest read after claim without delaying Player reload. Capture repositories and immutable event values before scheduling; never read a disposed Riverpod ref inside a builder. Copy mutable collections before scheduling.

`metricsRepositoryProvider` supplies storage; `metricsRecorderProvider` supplies the recorder. The optional third positional parameter on `EnsureDailyQuestsUseCase` is `MetricsRecorder?`; its provider injects `metricsRecorderProvider`. Existing two-argument callers remain valid.

`MetricEvents` columns: auto-increment `id`, DateTime `occurredAt`, text `localDate`, text `eventType`, JSON text `payload`. Store the supplied instant; derive localDate as YYYY-MM-DD from `occurredAt.toLocal()`. Original activity/Quest dates remain calendar strings. Wrap encoding/insert failures in Result.

## Canonical event payloads — version 1

The recorder injects `schemaVersion: 1` into every payload. This version is independent of Drift and CloudGameSnapshot versions. Use exactly these names/types in implementation and tests. Amounts are integers; IDs, date keys and outcomes are strings. All fields are required unless explicitly nullable. Do not add a redundant `success` boolean; use `outcome == 'success'`.

### health_sync

Record once after each successful sync, including zero-delta syncs:

```json
{
  "schemaVersion": 1,
  "totalNewRewardableSteps": 500,
  "dayCount": 1,
  "days": [{"date": "2026-09-10", "rewardableSteps": 500}]
}
```

Map SyncResult.days using DailySyncResult.date and rewardableSteps. dayCount equals array length; aggregate equals the sum. Failed syncs are not measured here. Catch-up dates remain original dates; total Steps are available in retained Health rows.

### energy_credited

Only emit after CreditEnergyFromStepsUseCase returns positive Ok<int>:

```json
{"schemaVersion": 1, "newRewardableSteps": 50, "energyGained": 1}
```

Existing pending remainder can make fewer than 100 new Steps yield positive Energy. No event for Ok(0) or Err. Health sync still records new Steps. Observation date is credit date, not the dates of all source Steps.

### adventure_attempt

```json
{
  "schemaVersion": 1,
  "adventureId": "greenwood_trail",
  "difficultyId": "hard",
  "suppliesSelected": true,
  "outcome": "success",
  "energyCost": 30,
  "expReward": 135,
  "goldReward": 54,
  "additionalGoldCost": 30,
  "energyBeforeObserved": 40,
  "energyAfter": 10,
  "energySpent": 30,
  "expGranted": 135,
  "goldGranted": 54,
  "goldSpent": 30
}
```

Outcomes: success, insufficient_energy, insufficient_gold, storage_error. Map existing expected validation failures to stable codes; never store raw failure messages. energyBeforeObserved is nullable when unavailable. energyAfter comes from returned Player on success and is null otherwise.

energyCost/expReward/goldReward/additionalGoldCost describe the requested option, including selected Supplies even when unaffordable. The four spent/granted fields are actual amounts: all zero on failure. On success they match the resolved costs/rewards. Net Gold is goldGranted minus goldSpent. Never infer tier from numeric cost.

Add required adventureId, difficultyId and suppliesSelected context to PlayerController.spendOnAdventure; update AdventureScreen and fake overrides. Preserve existing cost/reward parameters.

The UI currently rejects insufficient Energy/Gold before calling the controller. Record those branches through the recorder using this same schema. Controller logging covers only calls reaching it. Result dialogs do not emit another event. Preserve Energy-before-Gold validation order. Ignored duplicate taps and taps without loaded Player are not measured attempts. Maintain duplicate protection during a rejection dialog to prevent simultaneous duplicate interactions.

### quest_rollover

```json
{
  "schemaVersion": 1,
  "rolloverDate": "2026-09-10",
  "expiredCount": 1,
  "instances": [{
    "instanceId": "2026-09-09_daily_steps_1000",
    "questId": "daily_steps_1000",
    "date": "2026-09-09",
    "previousStatus": "inProgress",
    "progress": 200,
    "target": 1000
  }]
}
```

Keep a collection of instances whose expiry save returned Ok. Add each only after successful save. If a later save fails, record the nonempty successful collection before returning the original gameplay Err. After a fully successful loop, record once. Empty collections produce no event; expiredCount equals array length. Capture original status/progress before mutation.

This observes partial success without adding rollback or changing Quest transaction semantics. Retry queries active instances again, excluding already-expired instances; only newly successful expiries appear. Recorder failure does not alter the Quest result. Test first-save failure, later-save failure, full success and retry. Delivery remains best-effort.

### quest_claimed

```json
{
  "schemaVersion": 1,
  "instanceId": "2026-09-10_daily_steps_1000",
  "questId": "daily_steps_1000",
  "date": "2026-09-10",
  "expGranted": 10,
  "goldGranted": 5
}
```

Only schedule after a successful claim. Capture its instance ID and Quest repository; the recorder's async builder fetches getInstanceById. Build from the persisted claimed row's reward snapshot, never the caller's potentially stale instance. Require matching ID, claimed status and non-null claimedAt. Missing/invalid rows or read failures skip the event and log an instrumentation error.

Gameplay reloads Player and refreshes Quests without awaiting that read/write. The recorder captures occurredAt when claim succeeds, before the deferred read. This is observation time, not persisted claimedAt; exact claim timestamps remain queryable from Quest rows. Completion-to-claim delay remains deferred. Rejected/duplicate claims produce no event.
