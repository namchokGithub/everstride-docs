# Phase 6.1 — Balancing Metrics Instrumentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record the raw events `game-design/balancing.md`'s own "Metrics to record" section lists (health sync results, Energy credits, Adventure attempts, Quest claims/rollovers), so its "Measurement windows" (1–2 weeks of real use before any tuning) have real local data to look at. This is **not** a balance-value change — `balancing.md` explicitly forbids changing any number without that data first. This plan adds observation only.

**Architecture:** `game-design/balancing.md` is a measurement/process document, not a feature spec — unlike Phase 4/5/5.1, it has no MVP scope section and explicitly says it "does not declare the present values final or authorize an implementation change by itself." Its own "Balancing success criteria" does name one concrete gap, though: *"The app can capture or manually observe enough evidence to answer the core hypotheses"* — today it cannot; nothing in the codebase records Adventure attempts by difficulty, Quest claim/expiry rates, Energy earned/spent, etc. This plan closes exactly that gap: a local, append-only event log (`MetricEvents` Drift table) plus fire-and-forget logging calls at the points that already decide these outcomes. No aggregation, dashboard, or export is built — the doc's own phrasing ("capture **or manually observe**") makes querying the local SQLite file directly an accepted way to review this data for now.

**Tech Stack:** Flutter, Dart 3, Riverpod 3, Drift (one new table, schema migration 7 → 8 — confirmed against the current `app_database.dart`, which Phase 6 work has already carried to `schemaVersion 7`).

**Spec:** `everstride-docs/game-design/balancing.md`'s "Metrics to record" section. There is no separate technical spec — same situation as Phase 5.1 and Phase 6, both of which decided their concrete design during planning rather than reading it from a pre-written spec.

## Global Constraints

- **Metrics logging must never affect gameplay.** Every `logEvent` call from a controller is fire-and-forget (`unawaited(...)`) — a metrics failure must never delay, block, or fail the gameplay action it's observing, and must never surface as a gameplay `Err`. Log failures go to `AppLogger.error` only.
- **`MetricsRepository` lives under `lib/core/`, not a feature.** Every controller that logs an event (`health`, `player`, `quest`) would otherwise need to depend on whichever feature "owns" metrics — there is no natural owner, so this follows the same placement already used for `AppLogger` and `AppDatabase` itself: a `core/` utility every feature may depend on, with no feature depending on another because of it.
- **Payloads are a plain `Map<String, Object?>`, JSON-encoded into one `TEXT` column**, not a rigid per-event-type table schema. This project has exactly one instrumentation pass and no consumer yet parsing these programmatically — a fixed wide table with mostly-null columns per event type would be premature structure for data nobody queries from code yet. Revisit if/when a real aggregation feature reads this table back.
- **Not every metric `balancing.md` lists gets full precision in this pass.** In particular, "claim delay after completion" would need a `claimableAt` timestamp this project doesn't currently store on `DailyQuestInstances` — adding one is out of scope here (it would touch Quest's own schema for a metrics-only need). `quest_claimed` events record `claimedAt` and the instance's date only; a precise delay can be added later if this specific metric turns out to matter. Level distribution and Gold balance distribution need no event at all — they're already queryable directly from the `Player`/`player_saves` rows at any time.
- `EnsureDailyQuestsUseCase`'s constructor gains an **optional, nullable** third parameter (`MetricsRepository?`, defaulting to `null` via a positional-optional slot) specifically so its existing test file's six call sites (`EnsureDailyQuestsUseCase(questRepo, healthSyncRepo)`) keep compiling unchanged — this mirrors how `additionalGoldCost` was added to `SpendEnergyForAdventureUseCase` as an optional default in Phase 5.1.
- Reward-adjacent logic still gets a real test where there's a decision to protect: the use-case-level rollover logging (Task 2) gets one appended test. The controller-level logging additions (`HealthSyncController`, `PlayerController`, `QuestController`) get no automated test, matching the standing precedent for this project's controller-wiring code — verify with `flutter analyze` and the manual recheck in the final task.
- All commands below assume the working directory is `everstride-mobile/`.
- **Commit policy: not yet confirmed for this run.** Same standing note as every plan since Phase 4 — `everstride-docs/AGENTS.md` prohibits `git commit`/`flutter test` without per-run authorization, not requested yet for this plan. The last confirmed convention across Phase 3/3.1/4/5/5.1 was: authorized, no `Co-Authored-By` trailer. `git push` is never allowed, under any circumstance, for any run of this plan.

- [ ] **Step 6: Write the Drift-backed implementation**

The row→entity access below uses the Drift-generated row directly (no separate entity class) since this table has exactly one consumer (this repository) and one write path — introducing a parallel domain entity for a write-only log table would be the "empty layer" this project's own conventions warn against.

```dart
// lib/core/metrics/metrics_repository_impl.dart
import 'dart:convert';

import 'package:flutter_riverpod/flutter_riverpod.dart';

import '../database/app_database.dart';
import '../errors/result.dart';
import '../utils/app_logger.dart';
import 'metrics_repository.dart';

class MetricsRepositoryImpl implements MetricsRepository {
  MetricsRepositoryImpl(this._db);

  final AppDatabase _db;

  String _dateKey(DateTime date) =>
      '${date.year.toString().padLeft(4, '0')}-${date.month.toString().padLeft(2, '0')}-${date.day.toString().padLeft(2, '0')}';

  @override
  Future<Result<bool>> logEvent({
    required String eventType,
    required Map<String, Object?> payload,
    DateTime? now,
  }) async {
    try {
      final occurredAt = now ?? DateTime.now();
      await _db.into(_db.metricEvents).insert(
            MetricEventsCompanion.insert(
              occurredAt: occurredAt,
              localDate: _dateKey(occurredAt),
              eventType: eventType,
              payload: jsonEncode(payload),
            ),
          );
      return const Ok(true);
    } catch (e) {
      AppLogger.error('metrics.state', 'Failed to log metric event $eventType', e);
      return Err(Failure('Failed to log metric event', cause: e));
    }
  }
}

final metricsRepositoryProvider = Provider<MetricsRepository>((ref) {
  return MetricsRepositoryImpl(ref.watch(appDatabaseProvider));
});
```

## Phase 6.1 — Balancing Metrics Instrumentation

This phase has no visible UI change — verify by inspecting the local
