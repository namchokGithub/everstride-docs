# Phase 5.1 — Economy: Trail Supplies (first Gold sink) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Gold its first real use: an optional "Trail Supplies" toggle on the Adventure screen that spends 30 Gold for a ×1.5 EXP/Gold boost on that one Adventure run. This is the smallest possible realization of `game-design/economy.md`'s "preferred direction" (optional Adventure preparation) — no inventory, no shop, no persisted purchase record.

**Architecture:** `game-design/economy.md` is a principles/baseline document, not an MVP-scope document like `adventure-system.md`/`quests.md` were — it explicitly declines to choose a sink or set numbers, and explicitly forbids "placeholder spend buttons or a shop that cannot fulfill a purchase." The concrete design below (price, multiplier, UX) was worked out collaboratively with the user in this planning session, filling in the doc's own "Sink requirements" checklist, and approved before this plan was written. Because the boost applies only to the single Adventure resolution that's already in flight, this needs **no new Drift table and no new repository** — it's one new optional parameter on the existing `SpendEnergyForAdventureUseCase`, which already updates Energy, EXP, Gold, and Level atomically in one `Player` row write.

**Tech Stack:** Flutter, Dart 3, Riverpod 3. No new dependencies, no schema migration.

**Spec:** `everstride-docs/game-design/economy.md` (read this first — especially "Sink requirements", "Economic invariants", and "Failure and player-facing states", which this plan's design directly answers). This plan itself is the only place the concrete Trail Supplies numbers (30 Gold, ×1.5) are written down — there is no separate technical spec doc, matching how `economy.md` explicitly defers architecture to "the relevant future implementation plan."

## Pre-implementation corrections

These requirements supersede the earlier Task 1/2 snippets where they differ.

1. **One run means one run.** On a successful Adventure resolution,
   `AdventureScreen` must set `_useTrailSupplies = false` before pushing the
   result route. The bottom-navigation shell preserves the Adventure screen's
   state when the player returns, so leaving the checkbox selected would
   otherwise spend Supplies again on the next run without a fresh choice.
2. **Player mutations need one transactional boundary.** The Phase 5 Quest
   claim and Trail Supplies Adventure resolution can both read-modify-write the
   single Player row. A `PlayerController` mutex alone is insufficient because
   `ClaimDailyQuestUseCase` uses `QuestController`. Change
   `SpendEnergyForAdventureUseCase` to receive `AppDatabase` and execute its
   player read, Energy/Gold validation, reward calculation, and `savePlayer`
   inside `db.transaction()`. Its provider must pass `appDatabaseProvider`.
   This gives Adventure resolution and Quest claims the same Drift transaction
   boundary on the same database executor; neither may leave a stale Player
   write that discards the other's Gold/EXP/Energy change. Update its tests to
   use `AppDatabase(NativeDatabase.memory())` and `PlayerRepositoryImpl` for
   these transaction-sensitive cases.
3. **The successful UI fake must model net Gold.** In Adventure widget tests,
   `_SuccessfulPlayerController` must return
   `gold: _player.gold - additionalGoldCost + goldReward`, not just
   `goldReward`; tests must assert the result's Player balance for a Supplies
   run (Easy: `50 - 30 + 15 = 35`).
4. **Adventure widget tests must isolate Quest side effects.** Add a no-op
   `QuestController` fake and override `questControllerProvider` in every
   Adventure test harness. Successful Adventure tests call
   `recordAdventureCompletion()` asynchronously; leaving the real provider in
   place creates an unrelated database/controller side effect and makes the
   screen tests non-hermetic.

## Product balance decision — Trail Supplies earning horizon

- **Price:** 30 Gold per Adventure run.
- **Intended cadence:** A typical player should be able to choose Trail
  Supplies about once per local day, not automatically afford them for every
  Adventure.
- **Baseline:** Completing all current Daily Quests grants 25 Gold, so the
  player needs only 5 more Gold to afford Supplies. One Easy Greenwood Trail
  completion grants 10 Gold, leaving a 35-Gold balance before the purchase.
  This makes a Supplies run reachable through ordinary play without requiring
  a Hard run or a grind loop.
- **Trade-off:** On Easy, Supplies turn the displayed reward from 25 EXP / 10
  Gold into 37 EXP / 15 Gold, for a net Gold change of -15 after the 30-Gold
  price. The choice is therefore an optional short-term progression boost, not
  a self-funding purchase.
- **Review trigger:** Revisit the 30-Gold price and ×1.5 multiplier after
  observing typical Easy/Normal/Hard completions and Quest claims per active
  day. Do not tune either value in isolation.

## Global Constraints

- Trail Supplies is **not** an item, not inventory, not a purchase that persists independently of the Adventure it's used on. Toggling it just changes the arguments passed into the same, already-atomic `SpendEnergyForAdventureUseCase.call()` for that one resolution. Do not introduce a Drift table, a "purchase" repository, or a stock/count field for this — `economy.md` explicitly defers item inventory as a system.
- The boost is ×1.5 to EXP and Gold, **floor-rounded** (`(value * 1.5).floor()`), fixed 30 Gold price, all three difficulties, no stacking (checking the box twice does nothing extra — it's a per-run boolean, not a counter), no expiry (no timer — it either applies to the run just started or it doesn't).
- Per `economy.md`'s invariants: a failed Adventure attempt (insufficient Energy *or* insufficient Gold) must deduct nothing and grant nothing. `SpendEnergyForAdventureUseCase` must validate and save inside its shared Drift transaction (see Pre-implementation correction 2) — extend it, don't bypass it.
- The UI must never let the player *attempt* an unaffordable Trail Supplies purchase: the checkbox disables itself (with a "Need 30 Gold — you have N" caption) whenever current Gold is under 30. The use case's own Gold check is a race-condition fallback (Gold could change between the checkbox rendering and the tap), mirroring exactly how the existing insufficient-Energy dialog is both pre-checked in the UI and re-validated in the use case.
- `PlayerController.spendOnAdventure`'s new `additionalGoldCost` parameter defaults to `0`, so every existing call site (there is exactly one: `AdventureScreen`) and every existing test keeps compiling without needing a rewrite of its *behavior* — only the fake subclasses' method *signatures* in `adventure_screen_test.dart` need the new parameter added (Dart requires an override to repeat every named parameter the overridden method declares).
- No changes to `QuestController`/`RecordAdventureCompletionUseCase` — Trailbound still counts a completion regardless of whether Trail Supplies was used, unchanged from Phase 5.
- Reward-math changes get a real unit test (this project's standing testing priority) — the two new `SpendEnergyForAdventureUseCase` cases. `AdventureScreen`'s UI changes get widget-test coverage added to its existing comprehensive test file (matching the precedent Phase 4 set for this specific screen), not skipped as "just UI."

```dart
  Future<Result<PlayerState>> call({
    required int energyCost,
    required int expReward,
    required int goldReward,
    int additionalGoldCost = 0,
  }) async {
    if (additionalGoldCost < 0) {
      return const Err(Failure('Invalid additional Gold cost'));
    }
    final playerResult = await _playerRepository.getPlayer();
    final PlayerState player;
    switch (playerResult) {
      case Ok(value: final v):
        player = v;
      case Err(:final failure):
        return Err(failure);
    }

    if (player.energy < energyCost) {
      return const Err(Failure('Not enough energy'));
    }
    if (player.gold < additionalGoldCost) {
      return const Err(Failure('Not enough Gold'));
    }

    var newExp = player.exp + expReward;
    var newLevel = player.level;
    var expToNext = PlayerState.expToNextLevel(newLevel);
    while (newExp >= expToNext) {
      newExp -= expToNext;
      newLevel++;
      expToNext = PlayerState.expToNextLevel(newLevel);
    }

    final updated = player.copyWith(
      energy: player.energy - energyCost,
      exp: newExp,
      level: newLevel,
      gold: player.gold - additionalGoldCost + goldReward,
    );

    final saveResult = await _playerRepository.savePlayer(updated);
    if (saveResult case Err(:final failure)) {
      return Err(failure);
    }

    return Ok(updated);
  }
```

(Only the signature, the two new lines validating/checking `additionalGoldCost`, and the `gold:` line in `copyWith` changed — the level-up loop and everything else is untouched.)

import 'package:everstride/core/errors/result.dart';

  exp: 0,

class _SuccessfulPlayerController extends PlayerController {
  var lastEnergyCost = 0;
  var lastExpReward = 0;
  var lastGoldReward = 0;
  var lastAdditionalGoldCost = 0;
  PlayerState? lastPlayerAfter;

  @override
  AsyncValue<Result<PlayerState>>? build() => const AsyncData(Ok(_player));

  @override
  Future<Result<PlayerState>> spendOnAdventure({
    required int energyCost,
    required int expReward,
    required int goldReward,
    int additionalGoldCost = 0,
  }) async {
    lastEnergyCost = energyCost;
    lastExpReward = expReward;
    lastGoldReward = goldReward;
    lastAdditionalGoldCost = additionalGoldCost;
    final playerAfter = _player.copyWith(
      energy: _player.energy - energyCost,
      exp: expReward,
      gold: _player.gold - additionalGoldCost + goldReward,
    );
    lastPlayerAfter = playerAfter;
    return Ok(playerAfter);
  }
}

class _NoOpQuestController extends QuestController {
  @override

  @override

    required int expReward,
    required int goldReward,
    int additionalGoldCost = 0,

    required int expReward,
    required int goldReward,
    int additionalGoldCost = 0,

    return Ok(_player.copyWith(gold: 10));

  final _result = Completer<Result<PlayerState>>();

  @override
  AsyncValue<Result<PlayerState>>? build() => const AsyncData(Ok(_player));

  @override
  Future<Result<PlayerState>> spendOnAdventure({
    required int energyCost,
    required int expReward,
    required int goldReward,
    int additionalGoldCost = 0,
  }) {
    spendCallCount++;
    return _result.future;
  }

  void complete() => _result.complete(const Ok(_player));
