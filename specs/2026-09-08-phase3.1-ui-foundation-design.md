# Phase 3.1 — UI Foundation — Design

Status: approved, ready for implementation plan
Relates to: `everstride-docs/plan/EVERSTRIDE_PLAN.md` (inserted between Phase 3 and
Phase 4), mockup at `everstride-docs/image/draft_design.png`

## Goal

Replace the single debug-style Home screen with the real navigation shell and
visual language shown in the mockup: a persistent bottom-nav shell with five
tabs (Home, Adventure, Journal, Character, Menu), a first-run
Splash → Onboarding → Permission flow, and a reskinned Home dashboard — all
wired to data that already exists (Player state, health sync). No new game
logic is added in this phase.

Out of scope for this phase (left for their own phases, shown as placeholders
or trimmed here): the real Adventure difficulty-select flow and in-progress
screen (Phase 4), Journal/quest history (Phase 5), Character stats
(HP/ATK/DEF/SPD) and equipment (no such fields exist on `Player` yet — not
introduced here), Supabase-backed profile/auth (Phase 6, so Menu has no
working Sign Out), custom fonts/typeface, and a multi-page onboarding
carousel (mockup shows dots for one; this phase ships a single screen).

## Navigation architecture

`lib/app/router.dart` rewritten around `StatefulShellRoute.indexedStack`
(preserves each tab's state/scroll position independently — the standard
GoRouter pattern for a persistent bottom nav):

```
GoRouter(
  initialLocation: '/splash',
  routes: [
    GoRoute(path: '/splash', builder: (_, __) => SplashScreen()),
    GoRoute(path: '/onboarding', builder: (_, __) => OnboardingScreen()),
    GoRoute(path: '/permission', builder: (_, __) => PermissionScreen()),
    StatefulShellRoute.indexedStack(
      builder: (context, state, shell) => AppShell(navigationShell: shell),
      branches: [
        StatefulShellBranch(routes: [GoRoute(path: '/home', builder: (_, __) => HomeScreen())]),
        StatefulShellBranch(routes: [GoRoute(path: '/adventure', builder: (_, __) => AdventureScreen())]),
        StatefulShellBranch(routes: [GoRoute(path: '/journal', builder: (_, __) => JournalScreen())]),
        StatefulShellBranch(routes: [GoRoute(path: '/character', builder: (_, __) => CharacterScreen())]),
        StatefulShellBranch(routes: [GoRoute(path: '/menu', builder: (_, __) => MenuScreen())]),
      ],
    ),
  ],
)
```

`AppShell` (`lib/app/shell/app_shell.dart`) wraps `navigationShell` in a
`Scaffold` with a `NavigationBar`/`BottomNavigationBar` of 5 destinations
(Material icons stand in for custom icons: `Icons.home`, `Icons.explore`,
`Icons.menu_book`, `Icons.person`, `Icons.menu`), `currentIndex:
navigationShell.currentIndex`, `onDestinationSelected:
navigationShell.goBranch`.

### Splash routing logic

Extract the branching as a small pure function for testability:

```dart
String resolveSplashDestination({required bool onboardingCompleted}) =>
    onboardingCompleted ? '/home' : '/onboarding';
```

`SplashScreen` reads `AppSettings.onboardingCompleted` once via the settings
repository, calls this function, and navigates with `context.go(...)`. Onboarding
→ Permission → on completion, `PermissionScreen` (regardless of whether the
user actually granted the permission — this only gates whether onboarding
runs again, not whether Health Connect access exists) calls
`setOnboardingCompleted(true)` and navigates to `/home`. A user who already
completed onboarding always lands on `/home` directly; a later permission
revocation is handled by Home's existing inline denied-state banner, not by
re-routing back to `/permission`.

## Data model: `AppSettings` table

Add to `lib/core/database/app_database.dart`, following the same
single-row-at-id-0 convention as `Player`:

```
AppSettings
-----------
id                    int, fixed at 0 — single local settings row
onboardingCompleted   bool, default false
```

Bump `schemaVersion` 2 → 3:

```dart
@override
int get schemaVersion => 3;

@override
MigrationStrategy get migration => MigrationStrategy(
      onCreate: (m) => m.createAll(),
      onUpgrade: (m, from, to) async {
        if (from < 2) await m.createTable(player);
        if (from < 3) await m.createTable(appSettings);
      },
    );
```

## Architecture

New `features/settings` feature (the plan already reserves this slot; this is
its first real use), following the same layering as `player`:

- `lib/features/settings/domain/repositories/app_settings_repository.dart` —
  `abstract class AppSettingsRepository { Future<Result<bool>> getOnboardingCompleted(); Future<Result<bool>> setOnboardingCompleted(bool value); }`.
  Deliberately dumb CRUD, same reasoning as `PlayerRepository`: no branching
  logic belongs here, only persistence.
- `lib/features/settings/data/repositories/app_settings_repository_impl.dart`
  — Drift-backed; `getOnboardingCompleted()` returns `Ok(false)` if no row
  exists yet (first-ever launch); `setOnboardingCompleted()` upserts the
  `id = 0` row.

No controller/use case layer is needed for this feature — the repository
methods are called directly from `SplashScreen` and `PermissionScreen` (there
is no game logic to protect behind a use case, unlike `Player`).

## UI changes to existing files

- `lib/app/home_page.dart` is replaced by `lib/app/screens/home_screen.dart`
  — dashboard content only (see table above); the "Adventure (temporary)"
  button and its `spendOnAdventure()` call move to the new
  `lib/features/adventure/presentation/screens/adventure_screen.dart`. The
  "Pick a date" control moves to a calendar `IconButton` in Home's `AppBar`
  (replacing the mockup's notification bell — no notification system exists,
  so a fake bell icon is not added).
- The (now former) inline Health Connect availability/permission raw status
  text moves into `lib/features/settings/presentation/screens/menu_screen.dart`
  as a always-visible "Data & Sync" row (cleaned-up summary text, not the
  original debug-y enum-derived strings) — not `kDebugMode`-gated, since
  checking connection status is a legitimate thing for any user to do.
  `DebugStepsSeeder` moves into the same screen's `kDebugMode`-only "Debug
  Tools" section (it stays debug-only — real users never see it). Home keeps
  only the existing denied/unavailable *banners* it already shows inline
  (unchanged behavior, just restyled) — those gate real functionality
  (no steps to show without permission), unlike the raw status text, which
  added no actionable information once a banner already covers the bad case.
- `lib/app/theme/app_theme.dart` — new color tokens sampled by eye from
  `draft_design.png`: cream background, near-black/dark-teal for primary
  pill buttons, gold accent for EXP/Gold iconography, rounded card shapes.
  Refined visually during implementation; no new font dependency.
- `lib/main.dart` — unchanged apart from whatever `router.dart`'s rewrite
  requires (no new initialization beyond what already runs).
- `pubspec.yaml` — add `lib/assets/bg.png` under `flutter: assets:` (currently
  only `.env` is declared); used as the background banner on Splash and the
  Adventure tab.

## Error handling

`AppSettingsRepository` follows the established `Result<T>`/`Failure`
pattern, matching `PlayerRepository` — no exceptions cross the repository
boundary. A failed `setOnboardingCompleted` write during the onboarding flow
is logged (via `AppLogger`, same as other repositories) and does not block
navigation to Home — worst case, the user sees onboarding again next launch,
which is a harmless, self-correcting failure mode (not a data-loss risk like
Phase 2/3's reward math).

## Testing

Per the plan's own testing priorities (logic over UI), this phase's footprint
is deliberately light — there is no reward/progression math to protect here:

- `AppSettingsRepositoryImpl`: round-trip test (`get` returns `false` by
  default with no row; `set(true)` then `get()` returns `true`), mirroring
  `PlayerRepositoryImpl`'s existing test shape.
- `resolveSplashDestination`: unit test both branches (`true` → `/home`,
  `false` → `/onboarding`).
- One widget smoke test per new screen: renders without throwing, given fake
  provider overrides.
- One navigation test on `AppShell`: tapping each of the 5 destinations
  updates `navigationShell.currentIndex` / switches the visible branch.

No golden-image tests — there is no design-system/component library set up
to make those maintainable yet.
